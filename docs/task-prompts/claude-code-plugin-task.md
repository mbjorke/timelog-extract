## Context

Claude Code plugins of function hooks ("mods") can pin a status line, toast,
register slash commands and react to turn events, from a TypeScript module the
session hot-reloads. The statusline slices (`docs/task-prompts/gittan-statusline-task.md`)
already compute the right signal cheaply — project match plus today's unreported
hours from the observed cache, no collectors — but reach Claude Code only through
a classic `statusLine` setting with an absolute script path.

## Scope

1. **`gittan statusline [--cwd PATH]`** (`core/cli_statusline.py`): a thin command
   over `scripts/gittan_statusline.py::line_for`. Same line, same defensive
   contract (blank on any error), reachable through the installed `gittan`.
2. **`claude-code-plugin/`**: the plugin.
   - status line = `gittan statusline --cwd <session cwd>`, at session start and
     after each main-loop `turn.complete` (subagent turns skipped), always off the
     dispatch so a prompt never waits on gittan;
   - one toast per load when the line is the unconfigured-repo warning;
   - `/gittan [today|yesterday|week]` → `report <flag> --format json --quiet` →
     hours per project. JSON runs do not refresh the observed cache (by design,
     `core/report_cli.py`), so the status keeps saying `⟳ gittan report` until a
     terminal report runs; the plugin does not work around that.
   - `userConfig.command`: the gittan executable (default `gittan`).
3. **Generated mock fixture** (`scripts/build_claude_plugin_fixture.py`): a temp
   home, the real post-commit hook installed into neutral repos (`project-alpha`,
   `project-beta`, unmatched `scratch-notes`), commits that make the hook write
   central worklogs, then a terminal report (refreshes the observed cache), a
   JSON report and `statusline --cwd` per repo. Output, with the temp root and
   clock masked, is `claude-code-plugin/tests/fixture.ts`. `--check` exits 1 when
   stale; `tests/test_claude_plugin_fixture.py` runs it (skipped without zsh).

## Behavior

```gherkin
Scenario: Statusline follows the session
  Given the plugin is loaded in a session inside a configured repo
  When the session starts or a main-loop turn completes
  Then the status line shows `gittan statusline --cwd <cwd>` output

Scenario: Unconfigured repo is nudged once
  Given the repo matches no project profile
  When the status refreshes several times
  Then exactly one toast suggests `gittan map`

Scenario: gittan is missing
  Given the configured executable cannot start
  Then the status line says so and points at /config

Scenario: On-demand summary
  When the person runs `/gittan week`
  Then the plugin runs `gittan report --last-week --format json` and prints hours per project
```

## Findings along the way

- A profile with no `worklog` field gets commits appended to
  `~/.gittan/worklogs/<project_id>.md` by the hook, but the report only reads
  worklogs a profile names (`core/config.py::resolve_profile_worklog_paths`), so
  those entries are invisible. `gittan setup` writes the field, which hides the
  gap; hand-written configs hit it. Unknown repos' fallback worklogs have the
  same gap. Not fixed here — separate issue.
